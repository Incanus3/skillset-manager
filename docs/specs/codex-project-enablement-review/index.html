Codex enablement across worktrees

Enable one collection across a clone’s existing and future worktrees. Review what is shared, which links disable removes, and what survives an interrupted operation.

Accepted decisions: The design and implementation plan are approved. Execution starts after resumption. This page is a source-linked explanation, not implementation evidence.
01 / Scope and ownership

One clone shares registration; links remain local

Git's common directory defines the boundary. A second clone of the same remote has separate registration. Skill content stays under the inherited user home. Registration, Git hook and dispatcher are shared infrastructure; only Codex link projection is currently implemented.

D1 · Accepted

Project scope is explicit

--project covers registered worktree roots. --local keeps exact-current-directory behavior. Enable and disable still default to global scope.

Exact source contract
D2 · Accepted

Native hooks keep their own config

Git 2.54+ runs the named hook alongside existing hooks. The shared hook.skillset-project subsection invokes skillset _project-hook. No existing hook file or core.hooksPath is changed.

Exact source contract

02 / Link behavior

Disable removes matching links without origin tracking

D3 · Accepted A canonical link is recognized by its absolute normalized target, not by who created it.

Example: A starts with obra locally enabled; B starts without it
OperationWorktree AWorktree BClone registration
Before project enableCanonical local link presentNo linkNo registered obra
enable obra --projectKeep existing linkCreate canonical linkobra registered
disable obra --projectRemove pre-existing linkRemove canonical linkRemove obra after cleanup
Removal scope: All matching canonical links at registered worktree roots are removed, including pre-existing or tracked canonical links. Unrelated files and different-target links are preserved. Nested local links are outside project scope.

Local disable does not remove clone intent

Local disable succeeds as before. A later branch checkout or repeated project enable can recreate the link while its name remains registered.

No checkout means no trigger

worktree add --no-checkout alone creates no links. A later checkout or repeated project enable supplies reconciliation.

03 / Failure and recovery

Registration survives partial cleanup

D5 · Accepted Preflight rejects known problems before mutation. Once mutation starts, completed changes stay in place and the command returns an error until reconciliation succeeds.

The remaining registration controls what a later checkout can do
Failed operationPersistent stateRecovery and limit
Enable fails after recording intentNames retained; hook keys or links may be incompleteRepeat enable to finish, or disable a registered name to cancel. No all-worktree rollback.
Disable the last name failsName retained; owned hook may already be absent; links may be partly removedRepeat disable to finish. Enable restores hook and links.
Disable fails with other names registeredName retained; hook remains installed; links may be partly removedLater checkout can recreate the name being removed. Repeat disable; failure was not successful disable.
Listing: Ordinary codex list shows [g], [p] and [l] groups in that order. A physical local link and project registration can both appear for one name. Diagnosis: codex list --project is read-only. It shows registered names and reports missing sources, missing links, hook conflicts and inaccessible worktrees; health errors return 1. It does not repair state.

Exact source contract · Project inspection

Hook failure warns and leaves Git's status alone

D6 · Accepted Ordinary skillset hook failures write stderr and return zero to Git. A new worktree may therefore exist without its skills. Another hook's failure is still visible to Git.

The hook finds skillset through inherited PATH and uses inherited HOME. Python and Git must also be available. Missing sources are skipped without creating dangling links; valid names still reconcile.
